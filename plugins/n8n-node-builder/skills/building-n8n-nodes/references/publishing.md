## Pre-Publish Checklist

Before publishing, run the gate protocol in `references/validation.md`. Gates 1–3 must all pass:

- [ ] **Gate 1 — Lint:** `npm run lint` passes with zero errors (after `npm run lint:fix`)
- [ ] **Gate 2 — Build:** `npm run build` succeeds and the compiled files exist in `dist/`
- [ ] **Gate 3 — Cloud eligibility:** `npx n8n-node cloud-support` reports ENABLED (required for verification)

Then confirm the publish-specific items:

- [ ] Package name starts with `n8n-nodes-` or `@<scope>/n8n-nodes-`
- [ ] `package.json` has keyword `n8n-community-node-package`
- [ ] `package.json` has `n8n` attribute listing all nodes and credentials (paths to compiled `dist/` files)
- [ ] Node appears in the nodes panel when searching by `displayName` (Gate 4 smoke test)
- [ ] All operations function correctly with real API calls
- [ ] Credential test (the "Test" button) succeeds with valid credentials
- [ ] Icon displays correctly (square, no clipping)
- [ ] Codex file (`*.node.json`) has appropriate categories
- [ ] README with usage instructions exists (required for verification)
- [ ] `.github/workflows/publish.yml` exists (scaffold it with `n8n-node release --init-workflow` if missing)

## Testing Locally

Runtime testing is Gate 4 of the protocol — see `references/validation.md` for the full procedure, including the manual `npm link` method and the runtime troubleshooting map. The short version:

```bash
npm run dev
```

This compiles and starts a local n8n instance at `http://localhost:5678` with your node loaded. It watches for changes and auto-rebuilds.

### Testing tips

- Search for the node by its `displayName`, not the package name
- If changes don't appear, stop n8n, rebuild, and restart
- For webhook triggers, expose your local n8n (port 5678) with an external tunneling tool such as ngrok, localtunnel, or Cloudflare Tunnel, and set the webhook URL accordingly (the `n8n start --tunnel` option was removed in n8n 2.0)
- Test each operation with real API credentials
- Test error cases: invalid credentials, missing required fields, API errors

## Linting

The n8n linter is `@n8n/eslint-plugin-community-nodes`, run via the ESLint flat config `eslint.config.mjs` that `@n8n/node-cli` provides:

```js
import { config } from '@n8n/node-cli/eslint';
export default config;
```

**Do not edit this file.** The config also layers in the legacy `eslint-plugin-n8n-nodes-base` node/credential rules, so rule IDs appear as both `@n8n/community-nodes/<rule>` and `n8n-nodes-base/<rule>`.

```bash
# Check for issues:
npm run lint

# Auto-fix fixable issues:
npm run lint:fix
# or
npm run lint -- --fix
```

For the full rule catalog and fix patterns, see Gate 1 in `references/validation.md`. One example of how strict the rules are: every node class must declare the `usableAsTool` property (rule `@n8n/community-nodes/node-usable-as-tool`, error severity in both shipped configs, autofixable) — set it to `true` unless there's a specific reason not to. This is a lint failure, not merely a recommendation.

**Strict mode:** with `"strict": true` in the `n8n` config, `n8n-node lint` additionally verifies that `eslint.config.mjs` is byte-for-byte unchanged from the default (whitespace-normalized) and fails otherwise. Together with the default config (which includes the two cloud-only rules `@n8n/community-nodes/no-restricted-imports` and `no-restricted-globals`), this marks the package eligible for n8n Cloud verification. Manage it with `n8n-node cloud-support enable|disable` — `disable` warns that it makes the node ineligible for Cloud verification. See Gate 3 in `references/validation.md`.

**Never suppress rules with inline `eslint-disable` comments** — n8n's verification scanner ignores them entirely (see [Verification Guidelines](#verification-guidelines)).

### VS Code integration

Install the ESLint VS Code extension. The linter runs in the background and highlights issues as you type. Hover over issues for descriptions and quick-fix options.

## Package.json Requirements

### Minimum required structure

```json
{
  "name": "n8n-nodes-myservice",
  "version": "0.1.0",
  "description": "n8n nodes to integrate with My Service",
  "keywords": [
    "n8n-community-node-package"
  ],
  "license": "MIT",
  "homepage": "https://github.com/myuser/n8n-nodes-myservice",
  "author": {
    "name": "My Name",
    "email": "me@example.com"
  },
  "repository": {
    "type": "git",
    "url": "https://github.com/myuser/n8n-nodes-myservice.git"
  },
  "files": [
    "dist"
  ],
  "scripts": {
    "build": "n8n-node build",
    "build:watch": "tsc --watch",
    "dev": "n8n-node dev",
    "lint": "n8n-node lint",
    "lint:fix": "n8n-node lint --fix",
    "release": "n8n-node release",
    "prepublishOnly": "n8n-node prerelease"
  },
  "n8n": {
    "n8nNodesApiVersion": 1,
    "strict": true,
    "credentials": [
      "dist/credentials/MyServiceApi.credentials.js"
    ],
    "nodes": [
      "dist/nodes/MyService/MyService.node.js"
    ]
  },
  "devDependencies": {
    "@n8n/node-cli": "*",
    "eslint": "9.32.0",
    "prettier": "3.6.2",
    "release-it": "^19.0.4",
    "typescript": "5.9.2"
  },
  "peerDependencies": {
    "n8n-workflow": "*"
  }
}
```

Key points:
- The `n8n.credentials` and `n8n.nodes` arrays point to **compiled JS files** in `dist/`
- Every node and credential file must be listed here
- The `n8nNodesApiVersion` should be `1`
- `"strict": true` makes `n8n-node lint` enforce the unmodified default `eslint.config.mjs` and marks the package Cloud-verifiable (see [Linting](#linting))
- `"build": "n8n-node build"` cleans `dist/`, runs tsc, and copies SVG/PNG icon assets — no gulp needed (the old `tsc && gulp build:icons` setup is obsolete)
- `"prepublishOnly": "n8n-node prerelease"` blocks accidental direct `npm publish` — the command exits 1 unless `RELEASE_MODE` is set by the release flow. Do not remove it
- `@n8n/node-cli` must be a devDependency (>= 0.23.0 — earlier versions don't support the provenance flag); it provides the `n8n-node` bin and the `@n8n/node-cli/eslint` config that `eslint.config.mjs` imports
- Include `"files": ["dist"]` to publish only compiled output (not source)
- Use `MIT` license for verified community nodes
- `n8n-workflow` should be a **peer dependency**, not bundled — n8n provides it at runtime
- Populate `author`, `repository`, `license`, and `homepage` fields — npm metadata must match your public GitHub repo for verification

## Releasing

Releasing is a two-phase process: a local release command that versions and tags, and a GitHub Actions workflow that does the actual npm publish.

### Phase 1: Local release

```bash
npm run release
# = n8n-node release
```

Locally, this runs `release-it` with built-in prechecks that must all pass (full list in Gate 5 of `references/validation.md`): lint and build run as a `before:init` hook, and git must be on `main`, with a clean working dir, an upstream remote, and new commits to release. It then interactively bumps the version, updates the changelog (auto-changelog), commits, tags, pushes, and creates a GitHub release.

**It does NOT publish to npm** (`--npm.publish=false`). Pushing the version tag is what triggers publishing.

### Phase 2: GitHub Actions publishes

The pushed `*.*.*` tag triggers the scaffolded `.github/workflows/publish.yml`. Inside GitHub Actions (auto-detected via `GITHUB_ACTIONS`), `n8n-node release` runs lint, build, then `npm publish` with `NPM_CONFIG_PROVENANCE=true`. The workflow needs `permissions: { id-token: write, contents: read }` and authenticates via npm Trusted Publishing (recommended, no secrets) or an `NPM_TOKEN` repository secret.

If your project doesn't have the workflow yet:

```bash
npx n8n-node release --init-workflow
```

This scaffolds `.github/workflows/publish.yml` into the current project.

**Provenance is mandatory:** since May 1, 2026, n8n requires all community nodes submitted for verification to be published from a GitHub Actions workflow with an npm provenance statement — n8n won't accept verified nodes published from a local machine. A local publish is only possible with the discouraged `n8n-node release --publish` flag; packages published that way carry no provenance and cannot become verified community nodes. Do not bypass `prepublishOnly` to run a bare `npm publish` — that path is only viable for private, never-to-be-verified packages.

### First-time setup

- Create an npm account at https://www.npmjs.com/signup
- Set up publish access for the workflow (one-time, per package):
  - **Trusted Publishing (recommended):** on npmjs.com, package settings → **Publish access > Trusted Publishers** → add a GitHub Actions publisher with your repository owner, repository name, and workflow filename `publish.yml`. Leave `NPM_TOKEN` unset — GitHub's OIDC token is used instead.
  - **Token fallback:** create a Granular Access Token on npmjs.com scoped to the package and store it as the `NPM_TOKEN` secret in your repository's Actions settings.

After publishing, users install your node via: **Settings → Community Nodes → Install → `n8n-nodes-myservice`**

## Verification Guidelines

To get your node **verified** (discoverable in the n8n nodes panel without manual installation):

### Scope requirements

- Must not duplicate an existing n8n node — if your node is an iteration on an existing one, open a pull request against the existing node instead
- Logic and Flow-control nodes are not accepted
- Exactly **one third-party service per package** — a trigger node for the same service may ship in the same package, but packages wrapping multiple unrelated APIs or acting as a proxy layer for several services don't qualify. Submit each service as its own package
- n8n reserves the right to reject nodes that compete with paid enterprise features

### Technical requirements

- Start from the `n8n-node` CLI scaffolding — n8n strongly suggests (and one docs page says requires) it for verification submissions; it isn't strictly enforced, but your package must still pass all the n8n-node-based automated checks (lint, scan, provenance), which the scaffolding guarantees
- **No runtime dependencies** — precisely: the lint rule `no-restricted-imports` allows ONLY relative imports plus an allowlist: `n8n-workflow`, `@n8n/ai-node-sdk`/`ai-node-sdk` (see `references/ai-nodes.md`), `lodash`, `moment`, `p-limit`, `luxon`, `zod`, and `crypto`/`node:crypto`. Other Node.js built-ins (`fs`, `path`, `http`, ...) are banned
- No environment variable access, no filesystem access — `no-restricted-globals` bans `process`, `setTimeout`/`setInterval`, `__dirname`, `globalThis`, etc. (use `sleep` from `n8n-workflow` instead of `setTimeout`)
- Pass the linter with zero errors
- Published via GitHub Actions with an npm provenance statement
- English-only UI text
- MIT license

### Package source requirements

- The npm package's repository URL must match the public GitHub repository, and the git link must work
- The npm package author/maintainer must match the repository owner
- A README with usage instructions and authentication details is required (on npm or the public repo)

### How n8n vets packages

n8n checks published packages with:

```bash
npx @n8n/scan-community-package n8n-nodes-mypackage
```

The scanner verifies the npm provenance attestation and re-lints the **published artifact** with the full cloud rule set, ignoring inline `eslint-disable` comments (`allowInlineConfig: false`) — so suppressing rules with comments will not get a package past verification. Run the scan against your published package before submitting. Full details in Gate 6 of `references/validation.md`.

### UX requirements

- Follow n8n's UI design guidelines:
  - Title Case for parameter names, dropdown values, node name
  - Sentence case for descriptions, hints, tooltips
  - Resource → Operation pattern for multi-endpoint nodes
  - Additional Fields for optional parameters
- Use the same terminology as the service's GUI (not its API)
- Include helpful descriptions and hints
- Icon should be SVG, square aspect ratio

### Code quality

- TypeScript throughout
- Proper error handling with NodeApiError/NodeOperationError
- continueOnFail() support
- pairedItem linking for all output items (programmatic)
- No data mutation — clone input items
- Credential testing via `test` property

## Submitting for Verification

1. Ensure your node meets all requirements above (Gates 1–5 in `references/validation.md` pass)
2. One-time npm setup: on npmjs.com, package settings → **Publish access > Trusted Publishers** → add a GitHub Actions publisher (repository owner, repository name, workflow filename `publish.yml`) — or store a Granular Access Token as the `NPM_TOKEN` Actions secret
3. Publish to npm via the GitHub Actions workflow with an npm provenance statement (`npm run release` locally, then the tag-triggered `publish.yml` publishes — mandatory for verification since May 1, 2026)
4. Verify the published package: `npx @n8n/scan-community-package n8n-nodes-mypackage` must pass
5. Go to [n8n Creator Portal](https://creators.n8n.io/nodes)
6. Sign up or log in
7. Submit your package name for review

n8n will review your node for code quality, UX compliance, and security. They may request changes before approving.

Note: n8n reserves the right to reject nodes that compete with paid enterprise features.

## Troubleshooting

### "Credentials of type X aren't known"

The credential `name` in the node file doesn't match the `name` property in the credentials class. Ensure they're identical.

### Node doesn't appear in the nodes panel

- Check that it's registered in `package.json` under `n8n.nodes`
- Verify the path points to the correct compiled file
- Rebuild: `npm run build`
- Restart n8n

### Node icon doesn't show

- Icon must be in the same directory as the `.node.ts` file
- Must be SVG or PNG format
- The `icon` property must include `file:` prefix and the extension
- SVG must have a square canvas

### "API-Server cannot be reached" error

- Class name, file name, and package.json path must all be consistent
- Check that `displayOptions` reference existing property names

### Changes don't show after refresh

Every time you change description properties:
1. Stop the n8n process (Ctrl+C)
2. Rebuild: `npm run build`
3. If using npm link: re-run `npm link`
4. Restart n8n

When using `npm run dev`, changes rebuild automatically, but you may still need to refresh the browser.
